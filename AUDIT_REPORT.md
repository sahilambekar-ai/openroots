## Password/session security — item 2 (2026-10-26)

**Implemented and locally verified on `dev`.** Latest backend result: **451 passed, no failures, expected failures or skips**, including 13 PostgreSQL cases. Frontend helper tests: **13 passed**; production build, lint and types pass (11 existing lint warnings). The historical checkpoint-2 counts and open auth findings below are superseded here. No new coverage measurement was taken. Item 3 (email escaping, webhook limits and safe production configuration) is next.

- New passwords use **Argon2id**, explicitly configured at 19 MiB/two iterations/one lane. `argon2-cffi==25.1.0` is pinned. Successful legacy bcrypt login below 72 UTF-8 bytes upgrades the stored hash; inputs **at or above 72 bytes require verified email recovery**. The exact 72-byte boundary is rejected too, since it could be the prefix of a longer truncated password. This avoids silently binding an unverifiable suffix or accepting its truncated prefix. Existing shorter credentials remain usable, including old six-character reset passwords, until changed.
- Registration and reset now enforce **8–128 Unicode code points** in API/service/form checks. Login/reset no longer trim passwords; spaces and Unicode are preserved. Frontend registration/reset share a policy helper that counts code points rather than UTF-16 units.
- Account `session_version` and JWT `sv` enforce revocation on each authenticated request. Password reset, studio-managed teacher password changes and `/auth/logout` atomically increment it. **Logout signs out all devices**; existing unversioned JWTs will require a new login after rollout. Tokens get unique IDs. Reset also consumes every existing OTP and clears any stale recoverable teacher password. Lifecycle/suspension state stays unchanged. The web calls the logout endpoint before clearing storage; it reports outages and retains the credential for retry instead of claiming server revocation succeeded.
- Shared database counters limit password login (10/account/15min), verification (10/account/15min across OTP/reset), and issuance (5/account/15min plus 20/day across registration/login activation/OTP/reset). Source quotas span aliases and ignore arbitrary forwarded headers. Expiring HMAC-keyed counters, saturating atomic upserts, and a global allocation/traffic ceiling bound storage; no in-process fallback bypasses enforcement. Fixed-window boundaries permit bursts; the documented global capacity guard can deny legitimate traffic under attack. Proxy trust/edge protection still needs deployment verification.
- Migration **033_auth_security** adds only a default-zero session version and empty counter table. Fresh migrations through 032 then upgrade to 033 on a new disposable PG18.4 database preserve an existing hash/account. Unsafe downgrade is intentionally refused: old auth code cannot verify newly stored Argon2 passwords and would accept revoked tokens. Use a compatible forward fix; disaster recovery requires a coherent pre-release backup and signing-key rotation. No existing dev/UAT/production database was migrated.
- Regressions cover full-length ASCII/Unicode passwords, policy boundaries, exact spaces, legacy rehash/recovery, invalid/unversioned JWTs, all-device logout/reset/teacher-password revocation, quota normalization, request aliases, source rotation, daily windows, failed-request persistence, expired-row cleanup and bounded key insertion. PostgreSQL concurrency verifies exact quota admission, lossless revocation increments, single-use reset and login racing reset. A migration regression runs in the existing PostgreSQL CI suite.
- Production requirements re-audit: **0 reported advisories across 37 resolved packages**. Local browser smoke checks login/recovery/registration rendering; no real email, password/account changes, checkout or payment was submitted in the browser. Component/Playwright journeys remain item 5. Target Linux image and exact PG16 verification remain outstanding; Docker is unavailable locally.

Operational behavior, quotas, proxy trust and rollout/recovery steps are documented in [AUTH_SECURITY.md](progressrooms/progressrooms-api/deploy/AUTH_SECURITY.md). Evidence: `audit-evidence/2026-10-26/auth-security/`. Hash choices follow [OWASP password storage guidance](https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html) and [argon2-cffi guidance](https://argon2-cffi.readthedocs.io/en/stable/).

## 4. Changes, behavior and commit grouping

No commits were created. Logical change groups, all uncommitted on `dev`:

1. **Auth lifecycle/purpose (API):** `app/modules/auth/service.py` restricts OTP issuance and verification to server-defined LOGIN_VERIFICATION/EMAIL_VERIFICATION values; verification filters stored purposes. Requesting login OTP no longer consumes a reset OTP. Password reset changes credentials without changing verification, suspension, active or deletion state. Existing activation remains available through email verification. New regressions exercise endpoint aliases, invalid purposes, reset replay/expiry and lifecycle states. AUD-004/005 expected failures were converted to normal passing tests.

## 7. Security evidence and applicability

**Dependency tools.** npm audit queried current registry advisories for the lockfile. It reports 11 vulnerable package entries, including transitive/dev entries; runtime vs build exposure requires triage. The Sharp/Next image pipeline deserves priority because the configured runner is glibc Linux and remote HTTPS sources are unrestricted. The vendor SVG advisory states Sharp >=0.35.5 as a workaround; Next 15.5.28/16.4.1 contain that fix. This is a minimum for this advisory, not a guarantee the entire dependency tree becomes clean. Other Next findings remain. The Windows-specific critical advisory is not applicable to the shown Linux Docker target. See [vendor SVG advisory](https://github.com/vercel/next.js/security/advisories/GHSA-2464-fhr4-w9xw), [AVIF advisory](https://github.com/vercel/next.js/security/advisories/GHSA-2xp9-vwfh-vxw4), and [Windows advisory](https://github.com/vercel/next.js/security/advisories/GHSA-p293-qw3h-jr36).

pip-audit scanned exact installed venv versions, not a production image. Its 93 records include duplicates/aliases; 72 unique package+ID pairs remain before alias deduplication. Affected packages: certifi, Pillow, PyJWT, pytest, python-dotenv, python-multipart, setuptools and Starlette. Some are extra local/tooling packages. Runtime requirements are pinned for several affected packages; no dependency update or exploit simulation was done. FileResponse/multipart APIs appear in this application, making corresponding Starlette/multipart advisories worth explicit remediation tests.

**Bandit.** Seven low diagnostics. Labels such as bearer, Password Reset and None are false positives as secrets. The random.choices OTP helper is not called by the reviewed AuthService flow, which uses secrets.randbelow; it is a cleanup candidate, not proof active OTP generation uses a weak RNG. Rendering assert checks an internal kind that also has path guards. No blanket suppression or automatic cleanup was applied.

**Gitleaks.** Official v8.30.1 binary, published archive checksum verified. Scanned all locally available Git refs in each of the four repos, plus current directories. Two history findings: a truncated key example in AGENT_HELPER.md and a synthetic HMAC test secret in tests/test_commerce.py. Neither establishes a leaked active provider secret. Directory findings include ignored .env/private-validation secrets and generated Next encryption/preview keys; nested scans overlap. Sanitized saved output contains only paths, line numbers, rule IDs and commit/fingerprint metadata. No raw secret contents were copied into audit evidence. Remote-only/unfetched history was not scanned, and scanner silence does not certify absence of secrets.

**Selected controls reviewed.** Authentication decodes using the configured algorithm and checks expiry plus current user status; signed role claims do not replace database role checks. Tenant dependency binds organization membership and rejects inactive studios; existing isolation and role tests pass. SaaS webhook verifies HMAC, bounds streamed input, stores an event ledger and reconciles captured payment data; Zoom webhook checks HMAC and a five-minute timestamp window. Existing website rendering escapes text, restricts legacy image URLs to a fixed HTTPS host, disables downloader redirects and caps downloads; uploads use generated tenant-prefixed paths and a 5 MiB handler read cap. Bearer authorization headers, rather than ambient authentication cookies, are the reviewed auth mechanism, so cookie-CSRF controls are not assumed applicable. RichDescription strips tags/attributes before its reviewed innerHTML sink; this still needs adversarial browser tests. No general SQL/command injection was confirmed by this checkpoint's searches.

These observations are bounded source/test evidence, not a completed penetration test. Proxy-level request caps, TLS/security headers, actual production secrets, DNS email authentication, restore readiness and operational retention were not inspected.
